## Notes

- **What the check found.** `lib/chat-prompt.ts` already says the eval "builds its prompt from this same text", and `getKnowledge()` says the eval reads the same pack. `createChatHandler` takes a provider and options, so the eval can call the real handler in process. Nothing in the repo runs a model call outside the route: the e2e tests use a fake model API (D-061), and no test uses a real key.
- **What it runs against (D-062).** The handler in process, with the real provider and no rate limiter. The spec's pipeline says "against the preview", but the limiter allows 10 requests a minute and 60 a day per IP, so 50 cases (plus a re-run) against a deployed URL would be refused. In process is also the only way to read the raw citations, which `links` events don't carry.
- **How it runs.** Through Vitest, with its own config, so the `@/` alias resolves as it does for the unit tests. `npm test` doesn't pick it up (its `include` is `tests/unit/`). Plain Node can't resolve `@/`, and the project has no `tsx` (CODING § 1).
- **The judge (D-063).** `claude-sonnet-5-5`, a different and larger model than the one that answers, so a model isn't grading its own answers. It sees the question, the answer, the case's `must_not_claim` and the rubric for the case type, and returns one JSON verdict.
- **The key (D-064).** The eval needs a real key in GitHub Actions. That is a second exception to "secrets live only in hosting environment variables", next to D-024, and Caleb decides it. US-084 is his story to add it. Until it's added the workflow fails with a message that says why, rather than passing.
- **Points.** US-034 stays at 5: a case schema and 50 cases, graders, a judge, a runner, a workflow and their tests.
